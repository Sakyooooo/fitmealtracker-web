# 09. Apple Human Interface Guidelines の適用

出典: [Human Interface Guidelines](https://developer.apple.com/jp/design/human-interface-guidelines)
（本文は英語版の Foundations / Patterns / Components 各ページから取得。取得日 2026-08）

## このファイルの位置づけ

**HIG はこのプロジェクトの「プラットフォーム規範」です。**
01-references.md の他の 6 サイトが「引き出し」なのに対し、HIG は **数値と作法の基準**として扱う。
他のリファレンスと矛盾したときは **HIG を優先する**。

理由: FitMealTracker は `appleWebApp.capable` を設定し、`apple-icon` を持ち、
`viewport-fit=cover` でセーフエリアまで描画する **iOS ホーム画面前提の PWA**。
ユーザーはこのアプリを「iPhone のアプリ」として使う。ネイティブと作法がずれると、それは違和感になる。

### ただし Web である以上、そのままは適用できない

| HIG の前提 | Web / このアプリでの扱い |
|---|---|
| SF Pro / SF Compact | ライセンス上 Web フォントとして配信不可。**システムフォントスタック**で代替 |
| Dynamic Type（システム設定でテキストサイズ変更） | `rem` ベース + ブラウザのズーム/文字サイズ設定に耐える形で代替 |
| Liquid Glass（システムが提供するマテリアル） | `backdrop-filter` で**近似**する。用途は限定（§4） |
| SF Symbols | 使えない。ストロークベースの自前 SVG で統一（現行方針を維持） |
| Activity リング | **HIG が明確に禁止**しているので使わない（§6） |
| ハプティクス / Siri / ショートカット | iOS Safari では基本使えない。**代替手段を必ず用意する** |

## 1. 数値の基準（HIG 原文の値）

### 1.1 テキストサイズ

| プラットフォーム | 既定サイズ | 最小サイズ |
|---|---|---|
| **iOS, iPadOS** | **17 pt** | **11 pt** |
| macOS | 13 pt | 10 pt |
| watchOS | 16 pt | 12 pt |

- HIG は「カスタムフォントでもこの既定値・最小値に従え」と明示している
- **細いウェイトを避ける。** Regular / Medium / Semibold / Bold を使い、
  Ultralight / Thin / Light は使わない。細いカスタムフォントを使うなら推奨サイズより大きくする
- **テキストを 200% まで拡大できること**（HIG Accessibility）

→ 02-design-system.md §2.2 のスケールはこの値に合わせて改訂済み。

### 1.2 コントラスト

HIG が WCAG Level AA から引いている表:

| テキストサイズ | ウェイト | 最小コントラスト比 |
|---|---|---|
| 〜17 pt | すべて | **4.5:1** |
| 18 pt | すべて | 3:1 |
| すべて | **Bold** | 3:1 |

- 既定でこの比を満たせない場合、**最低でも「コントラストを上げる」設定が ON のときに高コントラスト配色を出す**
- ライト / ダークの両方で確認する
- 「同じ色を違う意味に使わない」。ブランド色をボタンにも非インタラクティブなテキストにも使うと混乱する

> **このプロジェクトの運用**: HIG の表は Bold なら 3:1 で可としているが、
> **日本語は同じ pt でも字画が多く潰れやすい**ため、02-design-system.md では
> 本文サイズのテキストは Bold でも 4.5:1 を要求する（厳しい側に倒す）。

### 1.3 タップ領域と間隔

| プラットフォーム | 既定のコントロールサイズ | 最小 |
|---|---|---|
| **iOS, iPadOS** | **44×44 pt** | **28×28 pt** |
| watchOS | 44×44 pt | 28×28 pt |

- HIG は **「サイズと同じくらい間隔が重要」**と明言している
  - 枠のある要素（ボタンなど）… 周囲に **約 12 pt** の余白
  - 枠のない要素（テキストリンク、アイコンのみ）… 見えている端から **約 24 pt**
- **複雑なジェスチャを常用動線に使わない。**マルチフィンガー / 独自ジェスチャを避ける
- **ジェスチャには必ず代替手段を用意する。**
  「スワイプで閉じる」を作るなら、タップで閉じるボタンも置く

## 2. レイアウト

- **コンテンツは画面の端まで伸ばす。**スクロール領域も下端・左右の端まで届かせる
- **コントロールとナビゲーションはコンテンツの「上の層」に浮く。**同じ平面に並べない。
  レイアウトはこの前提で組む（下部ナビの高さ分をコンテンツ側で確保する）
- コントロールとコンテンツの境目は **背景色ではなくスクロールエッジ効果**で示す
- 重要な情報から上・左（読み順）に置く。要素は揃える
- 一度に出せないときは **プログレッシブディスクロージャ**。
  「まだ続きがある」ことが分かる見せ方（項目の一部を覗かせる等）にする
- 端末の向き・画面サイズ・テキストサイズの変化に耐えること
- **最大・最小のレイアウトから先にテストする**（HIG 推奨の手順）

→ 現行の下部ナビは不透明な白 + `border-t` で「同じ平面」に見える。§4 で扱う。

## 3. モーション

HIG Motion の要点（04-motion.md はこれに沿って書かれている）:

- **意味なく動かさない。**過剰なモーションは注意を逸らし、不快感を与える
- **モーションを唯一の伝達手段にしない**（必ずテキスト等の代替を併置）
- **頻繁に起きる操作にはモーションを足さない。**
  「毎回目にする動き」は、その都度ユーザーの時間を奪う
- フィードバックのモーションは**現実的に**。
  上から出したものは上へ返す。横から出したものを下へ消さない
- **簡潔・正確に。**短く精密なフィードバックのほうが、大きなアニメーションより伝わる
- **モーションをキャンセルできるようにする。**アニメーションの完了を待たせない

### Reduce Motion のときの具体策（HIG 原文）

`prefers-reduced-motion: reduce` のとき、以下を行う:

- スプリングを締めて**バウンドを減らす**
- **ジェスチャに直接追従する**アニメーションにする
- **z 軸（奥行き）の変化をアニメーションしない**
- **x / y / z 軸の遷移をフェードに置き換える**
- **ぼかしに出入りするアニメーションを避ける**

> 「動きを消す」であって「機能を消す」ではない、という 04-motion.md §6 の方針と一致する。

## 4. マテリアルと Liquid Glass

HIG の現行デザイン言語は **Liquid Glass**。要点:

- Liquid Glass は **コントロールとナビゲーションのための層**で、コンテンツ層の**上に浮く**。
  下のコンテンツが透けて動くことで、階層と奥行きが生まれる
- **コンテンツ層に Liquid Glass を使わない。**アプリの背景などには標準マテリアルを使う
- **控えめに使う。**カスタムコントロールに乱用すると、コンテンツから注意が逸れる。
  **アプリの中で最も重要な機能要素だけに限定する**
- 2 つのバリアント
  - **regular** — 背景をぼかし輝度を調整して可読性を守る。テキスト量の多いもの（アラート、サイドバー）はこちら
  - **clear** — 強い透過。写真・動画の上に浮かせるとき用。
    **下が明るいときは 35% の暗いディミング層を敷く**

### Web での近似方針（このプロジェクトの決定）

| 場所 | 方針 |
|---|---|
| **モバイル下部タブバー** | `backdrop-filter: blur()` + 半透明背景で regular 相当を近似してよい。**面積が小さいので許容範囲** |
| デスクトップのサイドナビ | 不透明のままでよい（現行 `#0A0A0A`） |
| モーダルの背景オーバーレイ | **ぼかさない。**`bg-black/40` の単純な半透明（04-motion.md §4 — 大面積の blur はモバイルで重い） |
| カード・リスト・フォーム | **使わない。**コンテンツ層に Liquid Glass を持ち込まない（HIG の明示的な禁止） |
| 写真の上に重ねるコントロール | clear 相当。**下が明るいので 35% の暗い層を必ず敷く**（写真ライトボックスの閉じるボタン等） |

近似の実装形（下部タブバーのみ）:

```css
/* 面積の小さい固定バーに限定して使う */
background: rgba(255, 255, 255, 0.72);
backdrop-filter: blur(20px) saturate(180%);
-webkit-backdrop-filter: blur(20px) saturate(180%);
```

`backdrop-filter` 非対応・パフォーマンス不足時に不透明へ落ちるよう、**`background` を先に不透明で指定してから上書きする**。

## 5. パターン（このアプリに直接効くもの）

### 5.1 Feedback

- フィードバックは**情報の重要度と伝え方の強さを一致させる**
- **色・テキスト・音・ハプティクスなど複数の手段で伝える**（どれか 1 つに依存しない）
- ステータスは**それが説明している対象の近くに、邪魔にならない形で**置く
- **アラートは「重要かつ行動可能な情報」のためだけに使う**
- **予期しない・取り消せないデータ損失のときだけ警告する。**
  期待どおりの削除には警告しない
- **成功は基本的に知らせなくてよい。**人は成功を前提にしている。**失敗したときにだけ伝える**
  （十分に重要な操作の完了確認は例外）

### 5.2 Alerts（`window.confirm` を減らす根拠）

- **アラートは控えめに。**使いすぎると効果を失う
- **情報を伝えるだけのアラートを使わない**（行動できないアラートは嫌われる）
- **よくある・取り消せる操作には、破壊的であってもアラートを出さない。**
  メールやファイルの削除で毎回警告しないのと同じ
- 例外: **めったに行わない・取り消せない**破壊的操作にはアラートを出す
- **起動直後にアラートを出さない。**問題があるならキャッシュ済みデータ + 控えめなラベルで伝える
- タイトルは状況を簡潔かつ具体的に。「エラー」だけのタイトルは書かない

→ **記録の削除は「アラート」ではなく「Undo 付き Toast」が HIG に沿う。**
全データ削除・アカウント解除だけがアラート対象（03-components.md §9 と一致）。

### 5.3 Sheets / Modality

- シートは**現在の文脈に近い、範囲の限定されたタスク**のためのもの
- **一度に 1 枚だけ。**シートからシートを開かない（開くなら先に閉じる）
- **Done を置くなら必ず Cancel も置く**（保存せず閉じる道を必ず用意する）
- **モーダルの中に階層を作らない。**「アプリの中のアプリ」にしない
- **閉じる方法を必ず明示する**
- 複雑・長いフローはシートではなく全画面モーダルにする
- モーダルはタブバーを覆ってよい（一時的・自己完結だから）

### 5.4 Loading

- **できるだけ早く何かを表示する。**空白のままだと「壊れている」と受け取られる。
  プレースホルダのテキスト・図形・アニメーションを先に出し、届いた順に差し替える
- **待っている間も他のことをさせる**（バックグラウンドで読む）
- 進捗が分かるなら determinate、分からないなら indeterminate の表示を使い分ける

→ Gemini 解析中も、フォームの手入力を止めない設計が HIG に沿う。

### 5.5 Entering data

- **システムから取れる情報を人に入力させない**（時刻から食事区分を決める、等）
- **必要なデータを明確に。**プレースホルダだけでなくラベルを置く。妥当な既定値を入れておく
- **入力より選択を優先する。**キーボードがあってもリストから選ぶほうが速く、間違えにくい
- **入力した瞬間に検証する。**長いフォームを埋めた後で戻らせない
- 数値には数値フォーマッタ（Web では `inputMode` + 桁の整形）

### 5.6 Onboarding

- **速く・楽しく・スキップ可能に。**理想は「使えば分かる」こと
- **一度きりのオンボーディングより、文脈に応じた小さなヒント**のほうが学習に効く。
  説明は対象の UI の近くに出す
- スキップされたら次回以降は出さない。ただし後から見られる場所（設定など）に置く
- **システムや端末の使い方を教えない。**このアプリのことだけを教える

### 5.7 Undo and redo

- 人は**何度も undo できることを期待する**。回数を不必要に制限しない
- **undo の結果を見せる。**画面外で戻したものは、スクロールして見せる
- 結果を予測できるようにする（「削除を取り消す」のように対象を書く）

### 5.8 Workouts（フィットネス系アプリ固有）

- セッション中は**その時に必要なデータと操作だけ**を出す。関係ないもので気を散らさない
- **セッション中であることが一目で分かる見た目**にする
- **開始・停止のフィードバックを明確に。**操作は見つけやすく押しやすく
- **終了時にサマリー画面を出す**（→ Daily Recap はこの作法に合っている）
- **極端に短いセッションは破棄する**か、記録するかを尋ねる
- **動きながら読むことを前提に、大きい文字サイズと高コントラストで、重要な情報を読みやすく配置する**

> **これは現状のコードへの直接の指摘になる。**ジムセッション中の画面で
> `text-[10px]` / `text-gray-300` を使うのは、HIG のこの項目に真っ向から反する。

### 5.9 Charting data

- **すべてのデータをチャートにしない。**分析させる必要がないなら、リストや表で出す
- **チャートは単純に保ち、詳細は求められたときに出す。**詰め込むと関係性が見えなくなる
- **一般的なチャート型（棒・折れ線）を優先する。**見方を知っているから
- **チャートにアクセシビリティラベルを必ず付ける**（値と構成要素の説明、操作用の要素）

## 6. 使ってはいけないもの

### Activity リング

HIG は明確に禁止している:

- **Move / Exercise / Stand 以外の情報に使わない**
- **Activity リングを他の目的で複製・改変しない**
- **リング状の別要素で Move / Exercise / Stand の進捗を表さない**
- 表示する場合は 1 人分だけ。色を変えない。黒背景の上に置く

→ **このアプリでカロリー・PFC をリングで表現しない。**
横バー（現行の `PfcProgress`）が正しい選択。

### その他

- 絵文字をアイコン代わりに使わない（ui-ux-pro-max のチェックリストとも一致）
- 標準ジェスチャを再定義しない（3 本指スワイプ = undo など）
- タイマーで自動的に消える UI に重要な情報を置かない
  （処理に時間がかかる人・支援技術を使う人が読み切れない）

## 7. HIG と他リファレンスが衝突したときの優先順位

```
1. Apple HIG（09）              ← プラットフォームの作法・数値の基準
2. アクセシビリティ（05）        ← HIG より厳しい側があればそちらを採用
3. デザインシステム（02）        ← このアプリ固有のトークン
4. その他リファレンス（01）      ← 引き出し。1〜3 に翻訳してから使う
```

**具体的に HIG を優先した判断**

| 論点 | 他リファレンス | HIG | 採用 |
|---|---|---|---|
| 本文サイズ | Web 慣習の 14px | iOS 既定 17pt | **16px を既定**（HIG 寄り・Web の `rem` 慣習と両立） |
| 削除の確認 | 確認ダイアログ | 取り消せる操作に警告しない | **Undo 付き Toast** |
| ナビの見た目 | 不透明なバー | Liquid Glass の浮いた層 | **下部バーのみ半透明 + blur** |
| リング表現 | 見栄えがする | Activity リングの複製を禁止 | **横バーを維持** |

**逆に HIG を採らなかった判断**

| 論点 | HIG | このアプリ | 理由 |
|---|---|---|---|
| Bold テキストのコントラスト | 3:1 で可 | **4.5:1 を要求** | 日本語は字画が多く、同じ比でも潰れやすい |
| 大面積の blur | マテリアルとして推奨 | オーバーレイはぼかさない | Web の `backdrop-filter` はモバイルで重い（04-motion.md §4） |
| ダークモード | 単一モードでも両方の色を定義せよ | 現状は非対応 | 中途半端な対応は破綻する。**トークンを CSS 変数化した時点で着手する**（02 §1.5） |
